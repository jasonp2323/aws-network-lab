### Objective

Build an AWS environment in **us-east-1** where a WordPress application cannot reach its database or the internet unless Transit Gateway routing is correct, then deliberately break it six different ways and prove each root cause from logs. The deliverable is not a running product — it is a rig you can destroy and rebuild in ~15 minutes, plus a runbook of failure scenarios with known-correct evidence trails.

**Done means:** `curl https://lab.<yourdomain>` returns a WordPress page served by an ASG across 3 AZs; the app reaches RDS only via TGW; all egress leaves through a single NAT gateway in a separate hub VPC; the `app` and `dev` spokes cannot reach each other; and each of the six failure scenarios has been triggered once and root-caused from the log source named in its row.

**In scope:** three-plus-one VPC topology, TGW with per-attachment route tables, ALB + ASG + RDS, SSM-only access, flow logs / ALB access logs / CloudTrail / CloudWatch agent + alarms, and the failure runbook.

**Not in scope:** high availability that survives a region, WordPress performance or theming, secrets rotation, multi-account or Organizations structure, and CI beyond the HCP Terraform VCS pipeline itself.

The four design questions this plan opened with are now settled — see **Decisions** at the bottom for what was chosen and what each choice buys.

### Topology and TGW route tables

Four VPCs attach to one Transit Gateway. Each attachment is associated with **its own** TGW route table, and every route is static. The route tables — not security groups, and not VPC peering — are what decide who can talk to whom.

<Callout id="static-routes-callout" tone="decision">

**Static routes, not propagation.** Both `default_route_table_association` and `default_route_table_propagation` are disabled on the TGW, and no attachment propagates into any route table. Every entry is an explicit `aws_ec2_transit_gateway_route`.

Propagation would be less typing, but it makes routes appear and disappear automatically as attachments come and go — which means the _missing route_ and _blackhole_ scenarios become awkward to stage and easy to accidentally self-heal. Static routes make TGW genuinely load-bearing and let you break it from Terraform with a one-line change. `blackhole = true` is a first-class argument on that resource.

</Callout>

### CIDR plan

The second octet identifies the VPC on sight — `10.0.x` egress, `10.10.x` app, `10.20.x` shared, `10.30.x` dev. When you are reading raw flow-log lines at 2am during a mock incident, that saves you looking anything up.

TGW attachment subnets are dedicated `/28`s per AWS guidance: the attachment ENIs get their own subnets so they never compete for addresses with workloads, and so you can reason about the attachment's route table independently.

### Intra-VPC routing — where this actually breaks

TGW route tables are only half the path. Every packet also crosses two or three **VPC** route tables, and centralized egress has a return path that is easy to omit and produces a failure that looks like a firewall problem rather than a routing one.

<Callout id="egress-callout" tone="risk">

**The failure mode of a missing hop 5 is a hang, not an error.** Outbound SYN reaches the internet, the SYN-ACK reaches the NAT gateway, and the NAT has no route back to 10.10.0.0/16 — so the packet is dropped inside the egress VPC. From the instance it looks exactly like a security group or NACL blocking return traffic, and `curl` just sits there until it times out.

The tell is in the flow logs: the egress VPC's NAT ENI shows the inbound reply as ACCEPT, and the app instance's ENI shows nothing coming back. Worth staging on purpose once, because it is the single most common centralized-egress mistake and it does not resemble a routing problem from inside the box.

</Callout>

### Repository and HCP Terraform workspaces

State lives in HCP Terraform, so there is no `backend "s3"` block and no DynamoDB lock table. Applies happen in HCP runs triggered by merges to `main`, not from your laptop. Each workspace is VCS-driven against a **working directory** in one repo.

The one exception is `bootstrap/`, which runs locally with local state. It cannot live in HCP because it creates the IAM OIDC provider and role that HCP uses to authenticate to AWS — the workspace would need the role to exist in order to create the role. Run it once from your machine and keep its state file out of git.

`bootstrap/` also owns the **Route53 hosted zone**, and that placement is deliberate rather than tidy-minded. Destroying and recreating a hosted zone issues a fresh set of NS records, which would mean re-delegating at your registrar every single session. The zone is created once and survives every teardown.

### Apply order and dependencies

Cross-workspace values move through the `tfe_outputs` data source rather than `terraform_remote_state`. **Remote state sharing has to be explicitly enabled on each producer workspace** — otherwise the consumer's data source returns a 404 that reads like a permissions error. Wire run triggers `network → shared → app` so a network apply queues the downstream plans automatically.

<Callout id="destroy-callout" tone="warning">

**Destroy in reverse, and expect three things to fight you.** Queue destroy runs `app → shared → network → platform`; destroying network first leaves the downstream `tfe_outputs` data sources unresolvable and their destroy plans will error.

- RDS refuses to delete unless `deletion_protection = false` **and** `skip_final_snapshot = true`. Both are set deliberately in this lab; in anything real they are the opposite.
- S3 buckets holding ALB access logs and CloudTrail events refuse to delete while non-empty, so both carry `force_destroy = true`.
- TGW attachments take roughly 5 minutes each to delete and RDS multi-AZ around 10. A full teardown is ~15 minutes, which is normal rather than a hang.

`bootstrap/` is never destroyed.

</Callout>

### Observability, built to prove causes

The point of the logging here is not coverage, it is **discrimination**: given a symptom, which single source distinguishes a routing fault from a security-group fault from a host fault. That constraint drives three non-default choices.

**Flow logs use a custom format.** The default format omits `pkt-srcaddr`, `pkt-dstaddr`, `tcp-flags`, `flow-direction`, and `traffic-path` — which are exactly the fields that separate "the packet never arrived" from "the packet arrived and was refused."

**TGW flow logs are enabled alongside VPC flow logs.** They record which TGW route table made the decision, turning "TGW is probably the problem" into evidence.

**The `logs` interface endpoint is local to each VPC**, not reached over TGW. If CloudWatch ingestion depended on the TGW path, then breaking TGW would also destroy the evidence of breaking TGW.

<Callout id="journald-callout" tone="warning">

**journald needs a bridge, or you will ship nothing and not notice.** The CloudWatch agent reads log _files_; the systemd journal is a binary format it cannot parse. Pointing `logs.collect_list` at `/var/log/journal` produces a working agent, a healthy-looking config, and zero events.

Set `ForwardToSyslog=yes` in `/etc/systemd/journald.conf` so rsyslog writes plain text to `/var/log/messages`, and have the agent tail that. This is worth doing wrong once on purpose — silent log pipelines are a genuinely common production failure, and the only symptom is absence.

</Callout>

<Callout id="cert-callout" tone="decision">

**Scenario 6 is the most valuable one in the set, and it is the one that looks like nothing.** A TLS handshake that fails is rejected before the ALB ever produces a request, so it generates no access-log line, no target response, and no 5xx. Every dashboard stays green while the site is completely unreachable.

That gap is the lesson: _you cannot alarm on the absence of requests unless you decide to._ The lab therefore also alarms on `RequestCount` dropping to zero, which is the only signal that catches this class of failure.

Two mechanical notes. ACM will not import an already-expired certificate, so the swap uses a self-signed cert generated with a past `notAfter` and attached to the listener directly. And an ALB does **not** validate backend certificates at all — so an expired cert on the _targets_ changes nothing, which is why this scenario has to live on the frontend listener to be observable.

<Callout id="dev-spoke-consequence" tone="decision">

**The dev spoke is load-bearing for the thing this lab is meant to prove.** Adding it means
`envs/network/` builds four VPC attachments and four TGW route tables, not three — and
`tgw-rt-app` must have **no** route to `10.30.0.0/16` while `tgw-rt-dev` has **no** route to
`10.10.0.0/16`. Those two absences *are* the isolation control. A propagated route or a
default association would silently reinstate them, which is why default association and
default propagation are both disabled on the TGW.

The dev spoke needs only one subnet and one `/28` attachment subnet in a single AZ. It is an
isolation prover, not a workload.

</Callout>

<Callout id="stateless-consequence" tone="warning">

Stateless WordPress means the ALB must not depend on sticky sessions to look healthy, and
any media you upload while demonstrating the lab will vanish the next time the ASG replaces
an instance. That is intended. Do not "fix" it by adding EFS mid-session — it would add a
second failure domain while you are trying to isolate a routing one.

</Callout>
